# Token Optimization Benchmark

A benchmarking suite that evaluates AI coding agent configurations for **token efficiency** and **task completion accuracy**. For now it compares four tool strategies — Baseline, SymDex, Caveman, and Serena — by running Claude Code against realistic software engineering tasks inside isolated Docker containers.

## Overview

The benchmark runs a matrix of `tasks × tools × trials`, collecting token usage metrics and verifying correctness of the generated code changes. Results are written to a CSV file for analysis.

### Tools Compared

| Tool | Description |
|------|-------------|
| **Baseline** | Vanilla `claude` with no augmentation |
| **SymDex** | Claude augmented with [SymDex](https://github.com/husnainpk/SymDex) — an MCP-based semantic code search tool that indexes the codebase before the task |
| **Caveman** | Claude augmented with the [Caveman plugin](https://github.com/JuliusBrussee/caveman), which prepends `/caveman ultra` to the prompt for aggressive context gathering |
| **Serena** | Claude augmented with [Serena](https://github.com/oraios/serena) — an LSP-backed semantic coding toolkit exposed over MCP (`find_symbol`, `get_symbols_overview`, `search_for_pattern`) |

### Metrics Collected

- **Input tokens** — tokens consumed by the prompt and context
- **Output tokens** — tokens generated by the model
- **Cache hits** — `cache_read_input_tokens` (prompt caching efficiency)
- **Verification passed** — whether the generated code passes the hidden test harness (1 or 0)

## Project Structure

```
├── evaluate.py              # CLI entry point — runs the full benchmark matrix
├── tasks.json               # Task definitions (prompts + target commit hashes)
├── requirements.txt         # Python dependencies
├── Dockerfile.base          # Docker image for baseline and caveman tools
├── Dockerfile.symdex        # Docker image for symdex (includes symdex + MCP server)

├── benchmark/
│   ├── config.py            # RunConfig, Task, TaskResult dataclasses
│   ├── docker_runner.py     # Docker container lifecycle management
│   ├── metrics.py           # Claude JSON output parser for token metrics
│   ├── results.py           # CSV results writer
│   └── verifier.py          # Runs hidden test harnesses against container output
├── hidden_tests/
│   ├── verify_task_001.py   # Verification harness: humidity sensor feature
│   ├── verify_task_005.py   # Verification harness: accelerometer sensor feature
│   └── verify_mcp_usage.py  # Checks whether MCP tools were actually invoked (takes a server prefix)
├── scripts/
│   ├── baseline.sh          # Agent script: plain claude invocation
│   ├── symdex.sh            # Agent script: index → serve → claude with MCP
│   ├── caveman.sh           # Agent script: install plugin → claude with /caveman ultra
│   └── serena.sh            # Agent script: start Serena MCP server → claude with MCP
└── results/                 # Output CSV files and debug logs
```

## Tasks

Tasks are defined in `tasks.json`. Each task targets a specific git commit of the [moonraker-telegram-bot](https://github.com/nlef/moonraker-telegram-bot) project (checked out inside the Docker container).

| Task ID | Description |
|---------|-------------|
| `task_001` | Add humidity display for SHT3X sensors, including sensor name formatting |
| `task_005` | Add accelerometer support (ADXL345 / LIS2DW12) with magnitude calculation |

## Prerequisites

- **Docker** — images must be built before running
- **Python 3.11+**
- A `.env` file with your Anthropic credentials:

```
CLAUDE_CODE_OAUTH_TOKEN=your_token_here
```

## Setup

```bash
# Install Python dependencies
pip install -r requirements.txt

# Build Docker images
docker build -f Dockerfile.base   -t agent-benchmark-base   .
docker build -f Dockerfile.symdex -t agent-benchmark-symdex .
docker build -f Dockerfile.serena -t agent-benchmark-serena .
```

> The `caveman` tool reuses the `agent-benchmark-base` image and installs the plugin at runtime.

## Running the Benchmark

```bash
# Run all tasks, all tools, 1 trial each (default)
python evaluate.py

# Run 5 trials per combination
python evaluate.py --trials 5

# Run only the baseline tool
python evaluate.py --tools baseline

# Compare the two MCP-based code-search tools
python evaluate.py --tools symdex serena

# Run specific tasks against two tools
python evaluate.py --tasks task_001 --tools baseline symdex

# Custom results file and model
python evaluate.py --results results/my_run.csv --model claude-opus-4-5-20251001
```

### CLI Options

| Option | Default | Description |
|--------|---------|-------------|
| `--trials N` | `1` | Number of trials per task/tool combination |
| `--tools` | `baseline symdex caveman serena` | Which tools to benchmark |
| `--tasks` | all | Task IDs to run (e.g. `task_001 task_005`) |
| `--results` | `results/benchmark_results.csv` | Output CSV path |
| `--model` | `claude-haiku-4-5-20251001` | Claude model to use |

## Results

Results are appended to a CSV file with the following columns:

| Column | Description |
|--------|-------------|
| `Task_ID` | e.g. `task_001` |
| `Tool` | `baseline`, `symdex`, `caveman`, or `serena` |
| `Trial` | Trial number |
| `Input_Tokens` | Prompt + context tokens consumed |
| `Output_Tokens` | Tokens generated |
| `Cache_Hits` | `cache_read_input_tokens` |
| `Verification_Passed` | `1` (pass) or `0` (fail) |

Debug logs are written to `results/debug.log`.

### Sample Results

[`results/benchmark_results_3*3*2.csv`](results/benchmark_results_3*3*2.csv) contains a completed run of **3 trials × 3 tools × 2 tasks** (18 rows total). Key observations:

- All three tools achieved high pass rates; the one failure was `symdex` on `task_001` trial 2.
- **Cache hits dominate** — `cache_read_input_tokens` is 3–4 orders of magnitude larger than `Input_Tokens`, indicating heavy prompt-cache reuse across trials.
- **SymDex** tends to generate more output tokens (deeper exploration) while **Caveman** produces fewer, more targeted edits.
- **Baseline** is competitive on both tasks despite having no code-search augmentation.

## How It Works

For each `task × tool × trial` combination:

1. A Docker container is started with the target image
2. The tool script (`scripts/<tool>.sh`) is executed inside the container:
   - Checks out the target git commit
   - (SymDex only) Indexes the codebase and starts the MCP server
   - (Caveman only) Installs the Caveman plugin
   - (Serena only) Starts the Serena MCP server and registers it with `claude mcp add`
   - Runs `claude -p '<prompt>' --output-format json --dangerously-skip-permissions`
3. Token metrics are parsed from Claude's JSON output
4. The modified workspace is copied out of the container
5. The hidden verification harness is run against the output
6. Results are recorded to the CSV

## Adding New Tasks

1. Add an entry to `tasks.json`:

```json
{
  "id": "task_002",
  "type": "feature_impl",
  "commit_hash": "<git sha>",
  "prompt": "Your task description here...",
  "harness_verify_script": "hidden_tests/verify_task_002.py"
}
```

2. Create the corresponding verification script at `hidden_tests/verify_task_002.py`. The script should exit with code `0` on pass and `1` on failure.
